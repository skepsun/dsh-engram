# dsh-engram

> **[English](README.md) · [中文](README.zh.md) · [Русский](README.ru.md)**
 
Минималистичная долговременная память для [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness), дистиллированная из идей
[symbolic-index](https://github.com/skepsun/symbolic-index) и [pi-esr](https://github.com/skepsun/pi-esr) — с одной целью: **экономия токенов**.
 
- **Прием данных с нулевым участием LLM** — автоматически захватывает значимые события из результатов работы инструментов с помощью чистого
шаблонного сопоставления (милстоуны git с сообщением коммита `-m`, изменения ключевых файлов, повторяющиеся ошибки), а также явное хранилище `engram_store`. Ничто, что происходит в горячем
пути, не вызывает модель, а чистые операции — `git push` / `git stash` / тихие
коммиты — намеренно никогда не записываются (см. *Политику автозахвата* ниже).
- **Символический индекс + прогрессивное раскрытие** — компактный блок `[ENGRAM]` (по умолчанию
бюджет 700 символов ≈ 175 токенов; одна строка на память) внедряется при сборке промпта
и **заморожен для каждой сессии**, сохраняя префикс запроса стабильным по байтам для
повторного использования в Кэше KV. Агент углубляется с помощью `engram_recall` / `engram_detail` вместо
выброса сырых совпадений в контекст.
- **Протокол закрытия lite ESR** — `esr_task` / `esr_close` / `esr_link` предоставляют задачам
цикл жизни `draft → active → stable`, где `stable` требует реальных доказательств
(`artifact` / `evaluation` / `memory_ref`), выявляя пропуски закрытия вместо
позволения агенту объявлять победу без доказательств.
- **Уборка памяти (ограничения pi-esr)** — запланированный, механический, архивный
обход: воспоминания, истекший срок жизни (TTL), рабочие области с превышением лимита вытесняют
самые низкоценные записи, задачи, вышедшие из стабильного окна удержания, покидают
поверхность `[ESR]`, а "висячие" ребра ссыдок отбрасываются. Рабочий набор (активные
ссылки на задачи, воспоминания задач, проиндексированные попадания) никогда не трогается, и ничего не
удаляется полностью — каждая заархивированная запись сохраняет свой id и остается доступной для повторного извлечения.
- **Просмотрщик веб-интерфейса** — браузер памяти со статистикой в стиле бенчмарка и карточкой конфигурации,
построенный полностью на нативных слотах настроек DSH (без сторонних пакетов UI).
 
```
MIT   ·   node >= 22.19   ·   вместе host-half + browser-half в одном пакете
```
 
## Зачем нужен еще один плагин памяти?
 
Обзор существующей экосистемы плагинов DSH показывает, что ниши recall-bridge, approval-gate,
LLM-distillation и вектор/графовых структур уже переполнены. dsh-engram заполняет три пробела,
важные для дисциплины токенов:
 
1. **Никакой модели в пути записи** — захват детерминированно путем сопоставления шаблонов.
2. **Нет сырого текста в промпте** — внедряется ограниченный символьный индекс, извлечение остается
по требованию ("извлечено ≠ внедрено").
3. **Честное закрытие задач** — СТАБЛЬ не может быть объявлено без доказательств.
 
DSH уже предоставляет межсессионный FTS (`ctx.sessionQuery`), хранилище
(`ctx.storageDomain`), хуки внедрения промптов и слоты настроек; dsh-engram — это тонкий
слой композиции поверх них, а не полная ререализация.
 
## Установка
 
```sh
# из GitHub (это репозиторий)
dsh plugin --profile web add github:skepsun/dsh-engram
 
# после публикации в npm
dsh plugin --profile web add dsh-engram
 
# локальная разработка (symlink — изменения применяются немедленно)
dsh plugin --profile web add link:/path/to/dsh-engram
```
 
Затем **перезапустите `dsh web`**. Данные сохраняются в `~/.dsh/storages/dsh_engram.json`.
 
> Установки из npm и GitHub ниже не требуют **ручного шага зависимости**: pnpm
устанавливает `zod` и подставляет опциональные peers `@deepseek-ai/*` в
собственную `node_modules` плагина, а CLI автоматически регистрирует плагин в
`dsh.profile.bundles` профиля. Шаг `setup-links` ниже предназначен только для
рабочего процесса разработки `link:`, где pnpm намеренно не устанавливает зависимости
symlinked каталога.
 
> Для просмотра свежей сессии требуется запустить ее, чтобы увидеть внедренные блоки `[ENGRAM]` и `[ESR]` и инструменты; как промпты, так и реестр инструментов собираются за сессию.
 
### Зависимости для `link:` установок
 
*Symlinked* плагин разрешает свои импорты из собственной `node_modules`, поэтому
зависимости хост-стороны должны присутствовать **рядом с рабочим каталогом** — они не
отслеживаются git:
 
```sh
cd /path/to/dsh-engram
node scripts/setup-links.mjs     # одна команда: связывает @deepseek-ai
# пакеты рабочей области в node_modules И
# устанавливает zod (повторно используется из хранилища harness
# pnpm store или через `npm install`)
```
 
Скрипт автоматически определяет местоположение рабочего пространства harness по пути `../deepseek-harness` (также
работает, когда он находится рядом с *родительской* папкой репозитория, например, `E:\deepseek-harness` +
`E:\kototoro_demo\dsh-engram`); переопределить через `DSH_HARNESS_DIR`. Без этого
шага запуск `dsh web` завершится ошибкой `ERR_MODULE_NOT_FOUND: Cannot find package
'zod'` (а также обнаружит сбой на peers `@deepseek-ai/*`). Запуск `node
scripts/setup-links.mjs --check` выведет состояние, не записывая ничего.
 
## Что вы получаете в GUI
 
После перезапуска, внутри **нативной** поверхности настроек DSH:
 
- **Settings → Engram Memory** — автономный первоклассный раздел настроек (справа от раздела Plugins, не вкладка в нем). По умолчанию
вид "Все рабочие области" показывает воспоминания/задачи/ссылки каждой рабочей области,
сгруппированные по рабочей области (выпадающее меню + пагинатор рабочей области: область памяти
таблица дополнительно пагинирует 10 строк на странице с выпадающим списком перехода, фиксированной
шириной столбцов, эллипсисом контента с ограничением в 3 строки и полным текстом при наведении).
**Обзор**
карточки статистики (количество по рабочей области/типу, общее количество автозахватов, кумулятивные данные GC для рабочей области `[ENGRAM]` индекс токенов, общее количество GC), и искомая/
фильтруемая таблица памяти с действиями архивации + удаления, доска задач ESR с
встроенной формой "создать задачу" и функцией "заполнить доказательства для закрытия" для каждой задачи (artifact / evaluation / memory_ref → STABLE, те же гейты, что и esr_close),
список узлов + отношений (узлы — это доменные объекты, которые модель регистрирует через
esr_node — пакет/сервис/репозиторий/концепция; связи через esr_link) и панель
управления памятью GC (переключатель dry-run + кнопка запуска + отчет о указателях). Создание/закрытие используют нативные маршруты хоста `POST /api/dsh-engram/tasks` и
`POST /api/dsh-engram/tasks/close`. Проактивность со стороны модели определяется
внедренными блоками [ENGRAM]/[ESR]: многоэтапная работа получает задачу,
повторяющиеся доменные объекты получают узел, связанные задачи/узлы получают ссылку.
 
**Дистанционная телеметрия реального поведения (наблюдаемость агентов)** — страница ESR открывается
с панелью "поведение агента", получаемой из новой таблицы `usage` (сбор данных за рабочую область × день) + `GET /api/dsh-engram/stats`: каждый вызов инструмента `engram_*`/`esr_*` записывается (подсчеты, сбои, механика извлечения). Отчетные коэффициенты:
**Проактивность ESR** = вызовы esr / (память + вызовы esr); **коэффициент попадания извлечения**
= попадания, возвращающие ≥1 попадание / общее количество попаданий; **среднее число попаданий на запрос**;
**конверсия деталей** = engram_detail, следующий за попаданием извлечения в течение 8
сессионных событий. Подсчеты по инструментам + ежедневный отчет за 14 дней также показаны.
Цифры реальные, из реальных сессий — повысьте проактивность ESR, наблюдая за
этой панелью и настраивая внедренный промпт.
- **Settings → Plugins → Plugin configuration → dsh-engram** — сворачивающаяся
карточка настроек в том же стиле, что и встроенные карты "Shell / Agent loop / Web
поиск": заголовок + однострочное описание + хеврограф, свернута по умолчанию,
нажатие для развертывания/сворачивания. Открытие показывает ~12 опций в четыре группы —
Захват и поиск / Индекс / Жизненный цикл и GC / Безопасность. Изменения применяются к новым
сессиям (замороженные блоки остаются стабильными); Удалить / Сохранить с бейджем "не сохранено"
в заголовке. Карточка управляет пространством имен через собственные RPC настроек соединения (не через `isLoopback-gated` область), поэтому она остается редактируемой даже
когда GUI доступен через авторизованный туннель оператора.
 
Пагинатор браузер получ-половина обслуживается загрузчиком модулей клиента DSH непосредственно из этого
пакета (`dsh.client` + `exports["./client"]`, без пересборки веб-приложения); данные поступают из
петли ограждения `/api/dsh-engram/*` маршрута семьи. Ограждение по умолчанию закрыто; для доступа к просмотрщику памяти из авторизованного туннеля
хостнейм, укажите его в конфиге `trustedHosts` плагина (например, через реестр
или патч профиля):
 
```jsonc
// patch/engram.json
{ "engram": { "trustedHosts": ["cream-club-fragrances-caught.trycloudflare.com"] } }
```
 
Если вы измените `client/src`, пересоберите пакет с помощью:
 
```sh
npm run build:client
```
 
## Инструменты
 
| Инструмент | Назначение | Тип |
|---|---|---|
| `engram_store` | Явно сохраняет одну память (вид, теги, опциональный якорь сущности) | запись |
| `engram_recall` | Детерминированное ключевое слово извлечение из воспоминаний рабочей области; опциональный FTS `search_sessions` для прошлых сессий | чтение |
| `engram_detail` | Полная запись одной памяти (происхождение, теги, попадания) | чтение |
| `esr_task` | Создает запись задачи (черновик → активный) | запись |
| `esr_close` | Закрывает задачу через протокол доказательств (artifact + evaluation + memory_ref) | запись |
| `esr_link` | Добавляет типизированную связь между двумя сущностями (mini graph) | запись |
| `esr_gc` | Запускает уборку GC памяти для рабочей области (`dry_run:true` предпросмотры) | запись |
 
## Уборка памяти (Memory GC)
 
Планируемый обход (`gcIntervalHours`, по умолчанию 24ч) плюс ручная `esr_gc` /
кнопка GUI ограничивают хранилище способом pi-esr — **механический, защищенный рабочий набор, только архив**:
- Воспоминания, истекший срок жизни (TTL), архивируются (мягкие; id сохраняется, доступен через
фильтр архивированных в GUI);
- рабочие области с превышением лимита вытесняют самые низкоценные *незащищенные* воспоминания;
- задачи, прошедшие `gcStableRetentionDays`, архивируются и покидают `[ESR]`;
- связи, у которых **оба** конца удалены, отбрасываются (висячие края).
 
GC никогда не касается рабочего набора: воспоминания, ссылающиеся на активную задачу
(`memory_refs`), воспоминания типа задачи, и уже проиндексированные попадания
(`hits >= promoteHits`). Запуск `esr_gc` с `dry_run: true` для предварительного просмотра. Ничто
не удаляется физически — отчет заканчивается указателями для всех заархивированных элементов; ничего не было удалено.
 
## Политика автозахвата
 
Захват детерминирован и офлайн — он видит только *результаты* инструментов, а не
диалог. Что именно формирует запись памяти:
 
| Результат инструмента | Действие | Сигнал |
|---|---|---|
| `git commit … -m "subject"` | запись — написанный subject является памятью | 0.55 |
| `git merge` / `rebase` / `cherry-pick` / `tag` / `checkout -b` | запись (милстоун) | 0.5 |
| `git push` / `git stash` / commit без `-m`| **пропуск** — плеймбинг-эхо, а не решение | — | |
| запись/редактирование значимого конфига и пути документа | запись | 0.3 |
| чтение конфига | запись | 0.3 |
| повторяющаяся ошибка инструмента | запись (дедуплицировано по сообщению) | 0.25 |
 
Эксплицитные записи `engram_store` всегда записываются независимо от этих правил
(ограничено по сессиям).
 
**Кто получает индексную строку `[ENGRAM]`** (это то, что на самом деле попадает в промпт):
`signal >= minIndexSignal` **или** `hits >= promoteHits` **или** `kind === "task"`,
затем ограничено `indexMaxLines` / `indexMaxChars`. На дополнительный защитный блок
уходят echo команд git — текст, внедренный в цепочку оболочки
(`git push: cd … && …`) — остается вне индекса, даже когда выше сигнала
порога, пока попадания извлечения не промоутируют их. Все остальное тихо находится в
хранилище, доступно по требованию через `engram_recall` / `engram_detail` — "извлечено ≠
внедрено".
 
## Внедренные блоки
 
То, что модель видит на самом деле (рендерится один раз за сессию, затем замораживается):
 
```
[ENGRAM] workspace: symbolic-index · 2 memories · 1 task(s) active · 0 links
[D] 06-18 Решено: использовать sqlite-vec для извлечения #a2331d87
[T] 06-18 Обновление извлечения — АКТИВЕН · пропуск: artifact, evaluation, memory_ref #tsk_8b26
прокачка: engram_store (пользователь просит запомнить) | engram_recall <query> | engram_detail <id> | esr_task / esr_close / esr_link
 
[ESR] задачи: 1 активная / 1 стабильная
- tsk_0d: Обновление извлечения — АКТИВЕН · пропуск: artifact, evaluation, memory_ref
- закрытая: tsk_9a (RAG eval)  ·  +1
```
 
Префиксы: `[D]` решение · `[E]` ошибка · `[P]` процедура · `[F]` факт ·
`[I]` инсайт · `[H]` передача · `[T]` задача. Принадлежность следует за
*Политикой автозахвата* (порог сигнала / продвижение по извлечению / guard git-echo),
ограничиваясь настроенными лимитами линий и символов. `#` id адресовывает полные
записи через `engram_detail`. Когда у рабочей области нет задач, `[ESR]` все равно рендерит
одну строку, называющую `esr_task`/`esr_close`, чтобы механизм оставался видимым для
модели вместо исчезновения.
 
## Конфигурация
 
По умолчанию токен-осведомлены; можно переопределить любой ключ через патч профиля
(`~/.dsh/profiles/web/cordis.patch.yml`) или карточку настроек в веб-интерфейсе:
 
```yaml
- id: engram
  config:
    autoCapture: true        # захват результатов инструментов с нулевым LLM
    sessionSearch: true      # engram_recall также может выполнять FTS прошлых сессий
    autoCapturePerSession: 40
    indexMaxLines: 12        # Лимит строк [ENGRAM]
    indexMaxChars: 700       # Лимит символов [ENGRAM] (бюджет токенов)
    minIndexSignal: 0.4      # автозахваты ниже этого остаются вне индекса
                              # (вызовы git-команд исключаются независимо,
                              # пока не будут продвинуты попаданиями извлечения)
    promoteHits: 3           # ...пока не будут извлечены это количество раз
    expireDays: 180          # TTL памяти (0 = никогда)
    maxMemoriesPerWorkspace: 2000
    gcEnabled: true          # запланированная очистка памяти GC
    gcIntervalHours: 24      # частота обхода
    gcStableRetentionDays: 120  # задачи остаются в [ESR] после этого
    engramIndexOrder: 40    # порядок раздела systemPrompt (до блока инструментов)
    esrOrder: 41
```
 
## Разработка
 
```sh
npm test            # 29 тестов: core + web API + GC + usage-observability (node:test)
npm run eval        # офлайн-отзыв и бенчмаркинг структуры (детерминированный)
npm run build:client
```
 
### Тестирование и оценка (два уровня реального тестирования)
 
**npm run eval** (eval/recall-bench.mjs) — это детерминированный слой —
В стиле LongMemEval: контролируемый корпус (ASCII + CJK, известные теги/сущности/
метки времени), измеряемый через реальный путь хранилище/извлечение (openEngramDomain +
domain.recall), с отчетом о Precision@k / Recall@k / MRR / Hit@1 по каждому пробному запросу
(точный тег, подстрока, многотерм, CJK, фраза-единица, упорядочивание, отрицательный)
плюс метрики структуры в стиле StructMemEval (коэффициент дедупликации точных дубликатов,
покрытие якорями сущностей, гигиена "висячих" ссылок). Честные, воспроизводимые
числа — у всех будет одинаковый результат. Текущий запуск: AVG P@k 0.770 /
AVG R@k 1.000 / MRR 0.889 / hit@1 0.889 / 0 negative false-positives /
dedup 1.0.
 
**/api/dsh-engram/stats + панель наблюдения** — это слой реальной сессии —
он отвечает на вопрос, как модель на самом деле использует память в продакшене (ESR
проактивность, коэффициент попадания извлечения, конверсия деталей), тогда как eval
отвечает на вопрос о том, насколько хорош сам слой извлечения.
 
Структура репозитория: `lib/` (хост-часть: store / capture / index-block / tools / api /
settings), `client/` (браузерная часть, TSX + `build.mjs`), `test/` (node:test).
 
## Устранение неполадок
 
**Веб-интерфейс открывается и немедленно показывает "Не удалось загрузить плагины"** с ошибкой загрузчика, такой как:
 
```
failed to apply loader entry … (@linxin666/dsh-client-ui-web-ui-settings):
keyed slot "settings.plugin.item" требует options.key
```
 
Причина: DSH с версии `0.1.0-rc.7` объявляет слот конфигурации-карточки `settings.plugin.item` как **идентифицируемый по пространству имен настроек, которое редактирует карточка** —
что и делает карточка конфигурации dsh-engram (под `key: "dsh-engram"`). Семейство `@linxin666/dsh-web-ui-all` **до 0.2.0**
(`dsh-client-ui-web-ui-settings`) регистрировало свою группу карточек в этом слоте
**без `key`**, и поскольку одна неудачная загрузка лоадера прерывает всю
загрузку, GUI застревает на странице ошибки.
 
Исправления:
- **Правильное исправление — обновить семейство**: `@linxin666/dsh-web-ui-all@^0.2.x`.
Начиная с версии 0.2, оно переместило свой интерфейс настроек из индексируемого слота в
первый уровень `settings.section` (это upstream-исправление для этой конкретной ошибки).
- **Немедленное устранение неполадки**: добавить `key: "web-ui-plugins"` в ту единственную
`settings.plugin.item` регистрацию в установленном
`node_modules/@linxin666/dsh-client-ui-web-ui-settings/lib/client.js`, затем
перезапустить `dsh web`. (При диспетчеризации по пространству имен группа карточек просто
остается скрытой; ничего другого на странице не затронуто.)
