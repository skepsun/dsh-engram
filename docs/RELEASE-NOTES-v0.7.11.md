# dsh-engram v0.7.11

**L1 默认关闭，改为 opt-in。** 这不是修 bug，是承认结论。

## 1. 判决依据（两天的真机账本）

| 会话 | 请求 | 宿主自剪 | engram 自剪 | 备注 |
|---|---|---|---|---|
| `775f5173…` | 220 | 51,168 字符（4 次） | **0** | 只写过 1 次 todo，无完成项跨水位线 |
| `746c0362…` | 383 | 13,032 字符 | 7,841 字符（1 次） | 有 todo 进度，边界真的 fire 了 |

链条本身是通的——v0.7.7 修好工作区键（闸门），v0.7.8 修好 `session.append`
重入（执行），v0.7.9 修好两条腿归因（记账）。通的链条 + 空转的覆盖率：

- 宿主在**没有 engram 的情况下**就会剪（0.2.x 内置行为），普通会话里它全干完了；
- 我们的边界源只认 todo 完成 / goal 终态，而 ~62% 的会话根本没有 todo 进度；
- 有 todo 的会话里，我们确实**抢在宿主下一次装配之前**剪到了东西（7,841 字符）。

## 2. 改了什么

- `boundaryPrune` 默认 `false`（`resolveConfig` 与设置卡文案同步：需手动打开）；
- README 的 L1 小节改标题为 opt-in，并写入两天的实测对照；
- `test/settings.test.mjs` 的默认断言反转，并写明依据（不再是一句「v0.6 决定」）；
- `resultPack` 仍默认开——没有 `boundaryPrune` 时它自己退场（已有逻辑，无行为变化）。

## 3. 为什么不是「再调参看看」

idle cadence 那条路（每 N 请求触发）也能让普通会话开火，但它剪的是宿主**下一步就会自己剪**的
东西——重复劳动，只多付一次前缀失效。真正的问题不是触发条件太窄，是**宿主已经把这个活干了**。

留 opt-in 的理由只有一个：规划型长会话里，早剪确实比宿主压力驱动的晚剪省得多。
